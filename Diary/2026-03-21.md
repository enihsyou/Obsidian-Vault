## 升级 version-fox 到 v1.0

把 Windows 平台之前用的 v0.6 版本升级到最新的大版本，记录下之前和现在做的变更。

1. 下载镜像

```powershell
$env:VFOX_GOLANG_MIRROR = "https://mirrors.aliyun.com/golang/"
$env:VFOX_PYTHON_MIRROR = "https://mirrors.aliyun.com/python-release/"
$env:VFOX_NODEJS_MIRROR = "https://mirrors.aliyun.com/nodejs-release/"
```

2. 目录结构

- 之前是 `$HOME/.version-fox`，程序也兼容了旧目录，但向前看，还是换成新的 `$HOME/.vfox`
- 之前里面有个 `temp` 目录放 session 级别的信息，现在改为 `tmp` 了
- 用 [[需求应对软件#^c382dc |Link Shell Extension]] 把目录移动到内存盘
- 现在没有 [垫片 & PATH | vfox](https://vfox.dev/zh-hans/usage/shims-path.html) 了，得把 sdk 的 bin 各自加到 PATH 里，没了之前 [[收集可执行文件到 PATH]] 的优势，以后想办法弄回来

3. 全局安装并启用 SDK

```shell
vfox add golang
vfox add python
vfox add nodejs

vfox use golang@1.25.8 -g
vfox use python@3.14.3 -g
vfox use nodejs@25.8.1 -g
```

## aria2-zero 线程 CPU 占用持续不降

#未解之谜

换完 [[2025-12-11#在 Windows 平台使用上带本地化翻译的 aria2c]] 一段时间就观察到了，有时在 AriaNG 连上服务器后，aria2c.exe 进程的 CPU 持续保持在 6% 的水平不变。但苦于问题并不是毕现，这次终于又抓到了现场。

从 Process Explorer 提取的 Stack 信息结合 IDA 分析，线程是不断在执行 [`executeCommand > com->execute()`](https://github.com/zeromake/aria2-zero/blob/b33e08f6edb5431d9a89ddefb3f9d6c4433adda2/src/core/DownloadEngine.cc#L138)。命令好像都是 [`HttpServerCommand::execute()`](https://github.com/zeromake/aria2-zero/blob/b33e08f6edb5431d9a89ddefb3f9d6c4433adda2/src/network/HttpServerCommand.cc#L171)，在 `read` 等待 `recv` 填满缓存。

看到 TCP/IP 面板有许多处于 CLOSE_WAIT 状态的本地连接没有关闭，有非常多的其他 IO 动作（select 连接），估计是卡在这里了。

从 TCPView 来看，连接是很久之前创建的，在网卡上抓包没有奇怪的 FIN 包。
手动把连接掐断没能打断应用的卡死状态，先靠重启吧。

之前想有一种自动化方式监控进程 CPU 占用，过高就重启，但感觉不够智能还是算了。不排除是 aria2-zero 的 bug。

`2026-10-11` 又抓到了现场，这次应该能把原因缩小到 WinTLS 的 EOF 处理了。 #AIGC

主线程占满一个逻辑核心，在这台 16 线程的机器上就是约 6.25% 的总 CPU；每秒约 27 万次其他 I/O，读写 I/O 都是零。RPC 端口 6800 上有一条 `CLOSE_WAIT` 连接，对端是 Edge，同一连接在 Edge 侧处于 `FIN_WAIT_2`。说明 FIN 已经到达 aria2，只是它还没关闭连接。

查到 [`WinTLSSession::readData()` 处理 `recv() == 0` 的代码](https://github.com/zeromake/aria2-zero/blob/b33e08f6edb5431d9a89ddefb3f9d6c4433adda2/src/tls/wintls/WinTLSSession.cc#L496-L503)，这里为了先解密缓冲区里的数据，把 `closeConnection()` 注释掉了，只跳出读取循环。但后面只有解密得到 `SEC_I_CONTEXT_EXPIRED` 才会关闭连接；如果对端结束 TCP 发送时没有可处理的 TLS `close_notify`，缓冲区为空或只剩不完整的 TLS 记录，就可能一直保留 `st_connected` 状态，最后返回 `TLS_ERR_WOULDBLOCK`。

上层于是把 EOF 当成暂时没有数据，重新等待 socket 可读。可已经收到 FIN 的 socket 会持续可读，命令马上再次执行；`HttpServerCommand::execute()` 又会在每次可读时刷新超时计时，可能连 30 秒的超时都走不到。这样就能解释持续占用一个核心、其他 I/O 极高和连接留在 `CLOSE_WAIT` 的现象。之前以为是在等 `recv` 填满缓存，现在看来更可能是连接已经结束，却还在反复重试。
目前是源码和现场现象能对应上的推测，打算提交 issue 请作者确认。
